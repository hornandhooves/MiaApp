Si el calendario aprieta
El orden de corte es Diario, luego Bodas, luego Círculo. Lo que nunca se corta es la cadena que cuenta la historia: escanear, pedir, apartar, reservar. Sin esos cuatro el demo no demuestra nada, y con esos cuatro se sostiene solo aunque falte todo lo demás.

Tres capas y un principio: la app nunca habla con un tercero. Todo pasa por Cloud Functions, que es lo único que guarda credenciales y lo único que decide un precio. En el demo no hay terceros todavía, pero la forma ya queda puesta para cuando los haya.

Cómo funciona la sesión de invitado

Es la pieza que sostiene la promesa del producto: nadie crea cuenta para pedir un mezcal, y quien la cree después no pierde lo que ya gastó.

1
El sticker del camastro lleva un QR con un token firmado que incluye el spotId y un secreto que rota cada día.
2
La app hace signInAnonymously(). Firebase entrega un UID real sin un solo dato personal.
3
validarQR comprueba el token y escribe custom claims en ese UID: spotId, scope y vencimiento al cierre del día.
4
Las reglas de Firestore leen esos claims. Sin scope no hay escritura, y el scope del invitado nunca incluye abrir una puerta ni escribir en el ledger.
5
Si decide crear cuenta, linkWithCredential() enlaza la credencial al mismo UID. Sus pedidos y su folio siguen apuntando al mismo usuario, así que no hay nada que migrar. Por eso el anónimo es la primitiva correcta y no un atajo.

Las dos reglas que evitan los errores caros
El precio se congela en la línea del pedido al agregarlo, nunca se relee del catálogo al cobrar. Y el saldo de Olas es la suma del ledger, no un contador editable — así una promoción mal aplicada se revierte con un asiento en contra y queda auditada, en lugar de sobrescribirse.

Reglas deterministas del mock

Un demo donde todo siempre está disponible no convence a nadie. Estas reglas van en el adaptador mock, no en el seed, para que cualquier fecha que alguien pruebe dé un resultado creíble.

La Suite Premium no está disponible viernes ni sábado.
Dos categorías quedan con una sola unidad, para que aparezca el aviso de escasez.
Primera fila de camastros casi llena; la sombra de palapa libre.
El temazcal solo existe jueves y domingo. El yoga de las 9:00 con dos lugares.
Fechas a más de noventa días devuelven todo disponible, que es como se comporta un PMS real.

La forma de las reglas de Firestore

El archivo que hay que leer completo a mano. Esta es la forma; los tests de la semana 2 son uno por cada prohibición.

function tieneScope(s) {
  return request.auth != null
    && s in request.auth.token.scope
    && request.auth.token.exp > request.time.toMillis();
}

match /orders/{id} {
  allow create: if tieneScope('order')
    && request.resource.data.spotId == request.auth.token.spotId;
  allow read: if resource.data.uid == request.auth.uid;
  allow update, delete: if false;   // solo functions
}

match /ledger/{id} {
  allow read: if resource.data.uid == request.auth.uid;
  allow write: if false;            // solo acreditarOlas
}

match /roomTypes/{id} { allow read: if true; allow write: if false; }
Nota para las sesiones con Claude Code: este archivo y PLACEHOLDER_PRICES.ts son los dos que no se editan sin que tú los leas después. Son los únicos lugares donde un cambio silencioso cuesta confianza real en lugar de un bug visible.

# Mía Tulum · app móvil

Resort y beach club en Tulum. La app sirve a tres personas: el
huésped durante su estancia, el visitante de day pass, y el
viajero que todavía decide.

El diseño está definido en docs/prototipo.dc.html — veinte
pantallas, bilingüe. Es la especificación, no una referencia.
No inventes pantallas ni componentes que no estén ahí.

## Prohibido

- Un color, tipo, radio o espaciado que no esté en
  packages/ui/tokens.ts
- Un número de precio fuera de PLACEHOLDER_PRICES.ts
- Texto literal en JSX. Todo pasa por t('clave'), con entrada
  en es.json Y en en.json
- Leer Firestore desde una pantalla. Solo a través de los ports
  de packages/domain
- Editar firestore.rules o PLACEHOLDER_PRICES.ts sin decírmelo
  explícitamente en tu respuesta
- any, @ts-ignore, y console.log en código que se commitea

## Siempre

- TypeScript estricto
- Una tarea = una pantalla que corre en el simulador y se puede
  probar. No entregues capas a medias
- Objetivos táctiles de 44 pt mínimo
- Estados de vacío, carga y error en toda lista
- El precio se congela en la línea del pedido al agregarlo,
  nunca se relee del catálogo al cobrar
- El saldo de Olas se deriva del ledger. Nunca escribas un
  contador de saldo
- Toda escritura que cueste dinero lleva clave de idempotencia

## Estructura

app/(guest)/     las veinte pantallas
app/(staff)/     cocina y mapa, detrás de bandera
packages/domain/ ports, adaptadores, precios, reglas puras
packages/ui/     tokens y primitivas
packages/i18n/   es.json · en.json
functions/       Cloud Functions gen2
seed/            contenido del demo

Qué no poner en un prompt
·Las reglas que ya están en CLAUDE.md. Repetirlas gasta contexto y garantiza que las dos versiones se contradigan en tres semanas.
·El plan completo pegado. Dale la ruta como archivo y dile qué semana, no las siete.
·"Construye la app". Una sesión, una pantalla. Un alcance vago produce quince archivos a medias y ningún commit que puedas revertir.
·Capturas del prototipo. Tiene el código; leerlo le da los valores exactos, y una imagen solo le da una aproximación.

Un demo honesto sabe qué está fingiendo. Mantén esta lista viva en docs/ conforme construyas: es el puente entre este trabajo y la versión de producción, y es lo que va a pedir cualquiera que pregunte cuánto falta de verdad.
